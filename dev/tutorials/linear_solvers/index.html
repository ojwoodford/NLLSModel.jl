Linear Solvers & Sparsity

In nonlinear least squares, the normal equations at each iteration have the form:

\[(J^T W J + \lambda D) \Delta \mathbf{x} = -J^T W \mathbf{r}\]

Automatic Dense vs Sparse Block Selection

NLLSModel.jl automatically inspects the variable-cost bipartite graph (getvarcostmap(problem)):

  • For small or dense problems, it assembles the Hessian into a BlockDenseMatrix.
  • For larger sparse problems ($\ge 40$ total degrees of freedom with sufficient block sparsity), it assembles the Hessian into a BlockSparseMatrix and symmetrifies into a SparseMatrixCSC.

Selecting the Linear Solver Backend

Set the linsolver keyword in OptimizationOptions (or NLLSOptions):

  • :auto (default): Uses dense Cholesky (with QR fallback) for BlockDenseMatrix and static systems, and zero-allocation sparse $LDL^T$ (LDLFactorizations.jl) for BlockSparseMatrix.
  • :ldl: Uses LDLFactorizations.jl for sparse systems and Bunch-Kaufman symmetric indefinite factorization for dense/static systems.
  • :cholesky: Uses Cholesky factorization (with QR fallback if not positive definite) for both dense and sparse systems.
  • :qr: Uses QR factorization for maximum numerical stability on ill-conditioned systems.
using NLLSModel

options = OptimizationOptions(
    iterator = :levenbergmarquardt_dtd,
    linsolver = :ldl
)
res = optimize!(problem, options)

Eliminating Variables: reduction and storage

Whether eliminable variables (iseliminable, for example bundle-adjustment landmarks) are eliminated by a Schur complement is a choice about the layout of the linear system, so it is made where the system is built: by keywords of optimize!(model, options; reduction, storage) and of optimvars, not in OptimizationOptions. The optimizer eliminates exactly when the Hessian prototype it is given is a SchurBlockHessian. linsolver names only the solver for the system that is left (the reduced system, after elimination).

  • reduction = :auto (default) eliminates when the model has eliminable variables and the structure fits (each eliminable variable coupled only to retained variables; a variable of any size BlockLinearSystems takes as a block), and falls back to no elimination otherwise. :eliminate eliminates or throws an ArgumentError. :none never eliminates. Other values are an ArgumentError.
  • storage = :auto (default) stores the reduced system dense or sparse from the predicted fill of its Cholesky factor; :dense and :sparse force it. With nothing eliminated it chooses the storage of the Hessian itself in the same way: :auto decides from its block sparsity, :dense and :sparse force it.
  • max_dense_bytes (default 256 MiB) caps a dense matrix: :auto stores a larger one sparse, and :dense throws an ArgumentError giving its size.
optimize!(problem, options; reduction = :eliminate, storage = :sparse)

The same keywords, with the same rule, apply to formulation = :jacobian (the residual and the Jacobian). There the eliminated variables are eliminated by QR of their rows of the Jacobian, so JᵀJ is not formed for them: the prototype handed to the optimizer is a SchurBlockJacobian, and storage chooses the storage of the reduced system the same way. The Jacobian path also needs each eliminated variable to be in at least one cost.

Choosing a Configuration Automatically

recommendoptimizer chooses the formulation, reduction, storage, linear solver and iterator for a model by hand-written rules, from the model's structure and from one linearization and factorization of its Hessian at the model's current values. That probe measures the spread of the Hessian's diagonal, a lower bound on the condition number of the Jacobi-scaled Hessian, and how long a cost evaluation, a linearization and a solve take. When the Hessian is ill-conditioned, or cannot be factorized undamped, it also evaluates the Jacobian once and tests its rank along the Hessian's weakest direction: a rank-deficient Jacobian (a gauge freedom, say) keeps the Hessian path, where damping handles it, and a full-rank one goes to the Jacobian path, which does not square its conditioning. reduction and storage are what :auto builds; the other three choices follow the rules in its docstring. Every threshold in them is a starting value, not yet measured.

The result, an OptimizationRecommendation, explains itself when displayed. For a 2D pose chain of 30 poses with 40 eliminable landmarks, at its starting values:

The same choices, by hand (with SecondOrderOptimization loaded):
  optimize!(model,
      OptimizationOptions(iterator = :dogleg,
          linsolver = :cholesky);
      formulation = :hessian, reduction = :eliminate, storage = :sparse)

There are two ways to use it, with using SecondOrderOptimization:

  • optimize!(model, rec) runs the recommendation. Other keywords (maxiters, maxtime, the tolerances) go to OptimizationOptions; a keyword the recommendation sets is an ArgumentError.
  • Copy the printed call and change it as needed. The options are then fixed in the code, which also saves the one dynamic dispatch of building them from the recommendation's values.

A recommendation holds for the model and the values it was made from: it is not checked again when it is used.

Single Precision

precision = Float32 (a keyword of optimize!(model, options; ...), optimvars and optimvars_nls; default Float64) builds the linear system in single precision: the Hessian (with formulation = :jacobian, the Jacobian), its Schur or QR reduction and its factorization. Everything else stays in double precision: the variables, the residuals, each cost's derivatives (computed in Float64 and narrowed as they are added into the system), the cost, the gradient, the step and every test the optimizer makes. Because the gradient is exact, the optimizer converges to the double-precision answer, in the same or a few more iterations; inside the linear solve the system is conditioned by powers of two, so the single-precision factorization works on a well-scaled matrix.

julia> o = OptimizationOptions(iterator = :levenbergmarquardt);

julia> for T in (Float64, Float32)
           r = optimize!(deepcopy(model), o; reduction = :eliminate, storage = :dense, precision = T)
           println("precision = $T: ", r.niterations, " iterations, cost ", r.bestcost, ", converged ", isconverged(r))
       end
precision = Float64: 5 iterations, cost 2.0947539345256057, converged true
precision = Float32: 5 iterations, cost 2.094753934525606, converged true

(a bundle adjustment of 30 cameras and 1500 eliminated landmarks with noisy measurements.)

When it pays. Measured on one thread of an Apple-silicon machine, against Float64 on the same problem:

  • The system holds half the memory: bundle adjustment of 60 cameras and 5000 landmarks, 51 → 28 MB on the Hessian path with elimination, and 2.6 GB → 1.3 GB on the Jacobian path (dense reduced), 945 → 482 MB (sparse reduced).
  • A solve is faster where it is dominated by the factorization of a large dense matrix: 1.7× on the Jacobian path with a dense reduced system (3.8 s → 2.3 s per solve), 1.2× on the Hessian path (85 → 72 ms); elsewhere it is about the same, and on small problems nothing changes.
  • The iterations are the same on the Hessian path, and one or two more on the Jacobian path.

So single precision is worth it for a large problem whose linear system is the memory or the time: elimination with a large reduced system, or the Jacobian path's tables. On the Jacobian path, check the time on the whole run, not per solve (below).

When it does not. On an ill-conditioned problem (a monomial polynomial fit of degree 10 or more) the Hessian path in single precision does not converge: the Jacobian path, whose QR works at the condition number of J rather than of JᵀJ, is the remedy. A sparse Jacobian without elimination offers only :lsmr in single precision (sparse QR is double only), whose inexact steps may not converge. Some large sparse problems without elimination converged in double and not in single on the Hessian path too. Check the result's isconverged.

On the Jacobian path the single-precision QR loses accuracy where the residual at the solution is large against the gradient (its error grows with the residual; it is not refined), and the optimizer then takes rejected steps near the optimum. On bundle adjustments of 10 × 300 to 60 × 5000 cameras and landmarks with elimination and a dense reduced system (Levenberg–Marquardt, one thread, no time limit), Float32 took one to three more iterations and 1.6 to 2.0 linear solves per iteration (Float64: 1.0 to 1.1), stopped on lack of progress 6e-5 to 1e-4 from the Float64 solution, and spent 1.4 to 2.3 times as long in the linear solver, although each solve was 22 % to 36 % faster. There single precision saves memory, not time.

Which solvers offer it. Dense systems: every solver. Sparse systems: :ldl (and :cg, :minres, :lsmr with Krylov.jl), :cholesky where SparseArrays' CHOLMOD factorizes single precision (checked: Julia 1.13, not 1.10); sparse QR (:qr, and :auto where it means QR) is double only. A solver that does not offer single precision for the system is an ArgumentError when the system is built, naming those that do, so with sparse storage name the solver (linsolver = :ldl, or :cholesky).
