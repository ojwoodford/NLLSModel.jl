API Reference

NLLSModel — Module
NLLSModel

Nonlinear least-squares (and general smooth cost) problems as a bipartite graph of variables and costs: build a Model, and evaluate its cost, gradient and Gauss-Newton Hessian (optimvars) or its residual and Jacobian (optimvars_nls) for an optimizer. With SecondOrderOptimization loaded, optimize!(model, options) solves it directly.

Problem Representation

NLLSModel.Model — Type
Model{VarTypes, CostTypes}([variables])
Model(VT, CT)
Model(variables, CT)

Bipartite graph nonlinear least squares problem representation holding costs and variables.

Fields

  • costs: Container of cost and residual blocks that define the problem.
  • variables::Vector{VarTypes}: Vector of variable blocks.
  • varcostmap::SparseMatrixCSC{Bool, Int}: Variable-to-cost bipartite incidence matrix.
  • varcostmapvalid::Bool: Flag tracking validity of varcostmap.

Example

problem = Model(Float64, MyResidual)
addvariable!(problem, 0.0)
addcost!(problem, MyResidual(1.0))

NLLSModel.subproblem — Function
subproblem(problem::Model, unfixed) -> Model

Extracts a subproblem containing only the costs that touch an unfixed variable. unfixed takes the forms that the unfixed keyword of optimize! and optimvars takes: a variable index, a variable type, a Boolean mask over the variables, a list of variable indices, or nothing (all variables). NLLSModel.optimvars — Function
optimvars(problem::Model; unfixed=nothing, numthreads=StaticInt(Threads.nthreads()), reduction=:auto, storage=:auto, min_work=4000, min_work_cost=120, precision=Float64) -> (f, fdf!, x0, H)

The normal way to solve a Model is optimize!(model, options) (needs using SecondOrderOptimization); optimvars is the advanced route, for custom outer loops, reusing a workspace, or other solvers.

Constructs the objective function f, in-place gradient/Hessian evaluator fdf!, initial variable state x0, and Hessian template H for problem.

H is a prototype of the Hessian fdf!(g, H, x) fills, of the type the linear system stores it in:

  • one unfixed variable: an MMatrix{N, N, Float64} when its size N is static and at most 12, otherwise a Matrix{Float64}, zero-filled. The gradient buffer g is the matching vector type, an MVector{N, Float64} or a Vector{Float64}, which zero(H[:, 1]) builds. Buffers of exactly these types (deepcopy(H) and zero(H[:, 1])) are filled in place; any other AbstractMatrix/AbstractVector is filled through an internal copy on every call.
  • several variables: a SchurBlockHessian when variables are eliminated, a SparseMatrixCSC{Float64, Int} for a sparse system, and nothing for a dense one (pass a Matrix{Float64} and a Vector{Float64}).

Wrap the returned 4-tuple in a HessianObjective and pass it to SecondOrderOptimization.optimize!, then write the solution back into the model:

f, fdf!, x0, H = optimvars(model)
result = optimize!(x0, HessianObjective(f, fdf!; H), options)
syncvars!(model, fdf!, x0)

(optimize! needs a mutable x0; for a single variable of static size use optimize, which returns (x, result), and sync x.)

reduction and storage together decide H: it is a SchurBlockHessian exactly when elimination happens, and the optimizer eliminates exactly when it is handed one. Under elimination, storage = :auto chooses the reduced system's storage from the predicted fill of a Cholesky factor.

Keywords

The same for optimvars, optimvars_nls, flat_optimvars_nls, optimize!(model, options), NLPLSModel and NLLSNLSModel.

  • unfixed = nothing: which variables to optimize: a variable index, a variable type, a Boolean mask or a list of indices. nothing optimizes all of them; the others are left untouched.
  • numthreads = StaticInt(Threads.nthreads()): the most threads an evaluation uses (StaticInt or Integer).
  • reduction = :auto: whether eliminable variables are eliminated (the Schur complement). :auto eliminates when the model has iseliminable variables and the structure fits, and otherwise does not; :eliminate eliminates or throws an ArgumentError; :none never eliminates. The rule is the same on the Jacobian path (the residual and Jacobian, where the eliminated variables are eliminated by QR), which also needs every eliminated variable to be in a cost. The wrappers that hand a plain Jacobian to external solvers (flat_optimvars_nls, NLLSNLSModel) never eliminate: there :auto does not eliminate and :eliminate is an ArgumentError. A single unfixed variable is never eliminated under :auto, and :eliminate is an ArgumentError there.
  • storage = :auto: storage of the matrix the solver receives: the Hessian, the reduced system under elimination (on either path), or the Jacobian. :auto chooses from the structure (the sparsity of the Hessian, the predicted fill of the reduced system's Cholesky factor, or the fill of the Jacobian); :dense and :sparse force the choice. On the Jacobian path the Jacobian is a Matrix{Float64} or a SparseMatrixCSC{Float64, Int}, and optimize!(...; formulation = :jacobian) hands either to the optimizer. On the Hessian path a single unfixed variable's Hessian is always dense, so :sparse is an ArgumentError there.
  • max_dense_bytes = 268435456 (256 MiB): under storage = :auto a dense matrix larger than this is not chosen (it is stored sparse instead); under :dense a larger one is an ArgumentError saying how large it would be, raised before it is allocated. A single variable's Hessian has no sparse alternative, so above the cap it is an ArgumentError either way.
  • min_work: per-thread floor of the fill, in the work estimate of the formulation: on the Hessian path (the Hessian fill, forming JᵀJ and Jᵀr; default 4000) one number written, per cost m * n * (n + 1); on the Jacobian path (the Jacobian fill, writing r and J; default 280) one entry of r or J written, per cost m * (n + 1).
  • min_work_cost = 120: per-thread floor of a cost evaluation, one residual entry, per cost m.
  • precision = Float64: the element type of the linear system, Float64 or Float32 (anything else is an ArgumentError). With Float32 the Hessian (on the Jacobian path the Jacobian), its reduction and its factorization are single precision; the variables, the residuals, the cost, the gradient and the step stay Float64, each cost's derivatives are computed in Float64 and narrowed as they are added into the system. The byte counts of max_dense_bytes and of the dense-or-sparse decisions are of the system in this precision. Which solvers offer Float32 is DampedLinearSolve's table (its "Precision"); one that does not is an ArgumentError when the system is built. The wrappers that hand a plain system to external solvers (flat_optimvars_nls, NLPLSModel, NLLSNLSModel, nls_callbacks) take Float64 only.

Each kind of work is split over clamp(work ÷ floor, 1, numthreads) threads: one thread when its estimate is below twice the floor, and every thread at a floor of 0. The costs of each type are split into one chunk per thread, so the count is also never more than the largest number of costs of one type: a thread beyond that would have nothing to do. The Hessian fill uses at most 4 threads: each thread fills its own copy of the linear system, which costs work in proportion to the size of the system, so on large systems more threads were measured to be slower (the number of copies is also capped by memory). The defaults were measured on cheap residuals, on one machine; a costly residual could thread earlier than they let it.

Here m is a cost's residual length (1 for a general AbstractCost) and n the total dimension of its unfixed variables; each estimate is summed over all costs and computed once, at setup. The work of the residual functions themselves is not estimated.

NLLSModel.optimvars_nls — Function
optimvars_nls(problem::Model; unfixed=nothing, numthreads=StaticInt(Threads.nthreads()), reduction=:auto, storage=:auto, max_dense_bytes=268435456, min_work=280, min_work_cost=120, precision=Float64)

Constructs the residual and Jacobian callable structs (f, res!, resjac!, x0, J_proto) for problem.

There is no robust mode: each cost's kernel decides how its rows enter, as on the Hessian path.

What the kernel returns from robustifydcostRows of that cost
a linear kernel (NoRobust, or Scaled with a finite non-negative height)unweighted or scaled by a constant
second derivative zero (e.g. HuberKernel)IRLS: scaled by the square root of the first derivative
second derivative non-zero (e.g. Huber2oKernel)IRLS with the Triggs correction

So choosing first- or second-order treatment means choosing the kernel type. resjac!(r, J, x) returns the true cost cost(model) at x; this equals ½‖r‖² only when islinear(resjac!) is true.

J_proto is a Matrix{Float64} or a SparseMatrixCSC{Float64, Int}, chosen by storage. In place of a dense prototype, resjac! takes any dense AbstractMatrix of its size (SecondOrderOptimization hands it an MMatrix copy, and an MVector for r, when it solves a small single static variable with its static system). With elimination (reduction) it is a BlockLinearSystems SchurBlockJacobian{Float64, RType}: one table per eliminated variable, holding the rows of the costs that involve it, and tables for the other costs. resjac!(r, J, x) then writes each cost's residual and Jacobian rows into its table, and leaves r alone (pass any vector, for example an empty one); res!(r, x) still writes the whole residual into r. RType, Matrix{Float64} or SparseMatrixCSC{Float64, Int}, is the storage of the reduced system, chosen by storage and max_dense_bytes by the Hessian path's rule. x0 then holds the unfixed variables in the partition's order, retained first; syncvars! writes a solution back.

What optimize!(model, options; formulation = :jacobian) does with each prototype:

reductionstorageJacobian prototypelinsolver
no eliminationdenseMatrix{Float64}:auto, :qr; :cholesky, :ldl (the normal equations, formed from J); :lsmr (with Krylov.jl)
no eliminationsparseSparseMatrixCSC{Float64, Int}:auto, :qr; :lsmr (with Krylov.jl)
eliminationdenseSchurBlockJacobian{Float64, Matrix{Float64}}:auto, :qr, :cholesky, :ldl; :lsmr (with Krylov.jl)
eliminationsparseSchurBlockJacobian{Float64, SparseMatrixCSC{Float64, Int}}:auto, :qr, :cholesky, :ldl; :lsmr (with Krylov.jl)

reduction and storage are as for the Hessian path, :auto included: elimination when the model has eliminable variables and the structure fits (on the Jacobian path also: each eliminated variable is in a cost), the reduced system stored by the Hessian path's rule, and without elimination the Jacobian's storage from its fill, never dense above max_dense_bytes. The linsolver values are those SecondOrderOptimization accepts for each prototype: its rules, the linear system of each row and the iterators it takes are in the "Supported combinations" table of its JacobianObjective docstring. Any other combination is an ArgumentError before anything is evaluated.

NLLSModel.flat_optimvars_nls — Function
flat_optimvars_nls(problem::Model; unfixed=nothing, numthreads=StaticInt(Threads.nthreads()), reduction=:auto, storage=:auto, max_dense_bytes=268435456, min_work=280, min_work_cost=120, precision=Float64)

Constructs a flat Euclidean vector wrapper around optimvars_nls. Returns a NamedTuple (; f, res!, resjac!, jac!, x0, J_proto, layout, status). Its Jacobian is a plain matrix, for external solvers, so it never eliminates: reduction = :auto does not eliminate here, and :eliminate is an ArgumentError. Accepts any unfixed variable whose update is plain addition, update(v, δ) ≈ v + δ, and that packs into a flat Float64 vector: a number, or an AbstractVector of numbers that can be built from a vector of its values (Float64, SVector{N, Float64}, Vector{Float64}, or a type of your own). Nothing needs declaring: each variable type is checked numerically, once, here. A type that cannot be packed, or whose update is not addition, is an ArgumentError saying which.

NLLSModel.islinear — Function
islinear(fn) -> Bool

For the evaluators returned by optimvars_nls (res! or resjac!) or the named tuple returned by flat_optimvars_nls: true when every cost is a non-adaptive residual with a linear kernel (NoRobust, or Scaled with a finite non-negative height). Then r is the true (constant-scaled) residual and the cost returned is exactly ½‖r‖², which solvers that derive the cost from r rely on. Otherwise some rows are reweighted and the cost is the robust cost, not ½‖r‖².

Solving a Model

With using SecondOrderOptimization, a package extension adds methods to its functions:

  • optimize!(model::Model, options = OptimizationOptions(); formulation = :hessian, callback, workspace, unfixed, numthreads, reduction = :auto, storage = :auto, max_dense_bytes, min_work, min_work_cost) -> result solves the model and writes the solution into model.variables. formulation = :jacobian solves from the residual and the Jacobian (see the home page).
  • optimize(model::Model, options = OptimizationOptions(); kwargs...) -> (model_copy, result) does the same on a copy.
  • optimize!(model::Model, rec::OptimizationRecommendation; callback, workspace, min_work, min_work_cost, options...) -> result solves the model as a recommendation from recommendoptimizer says; the other keywords go to OptimizationOptions. optimize(model, rec; kwargs...) does the same on a copy.

The keywords after workspace are the set every entry point takes, described under optimvars and in Linear Solvers & Sparsity. For custom outer loops use optimvars and HessianObjective directly.

workspace is nothing, a SecondOrderOptimization OptimizationWorkspace (the optimizer's state is reused, the model's setup is built for each call) or a ModelWorkspace (both are reused):

NLLSModel.ModelWorkspace — Type
ModelWorkspace()
ModelWorkspace(model::Model, options = OptimizationOptions(); formulation=:hessian, unfixed=nothing, numthreads=StaticInt(Threads.nthreads()), reduction=:auto, storage=:auto, max_dense_bytes=268435456, min_work, min_work_cost=120, precision=Float64)

A workspace for repeated solves of a model: pass it as optimize!(model, options; workspace). It holds the model's setup (what optimvars or optimvars_nls builds: the linear system's layout, its storage and the functors) and the optimizer's OptimizationWorkspace (its linear system, factorization and iterator state), so a repeated call builds neither. Both constructors are defined when SecondOrderOptimization is loaded.

A call reuses the setup when it is for the same Model object, with the same variable vector, the same structure and the same keywords (formulation, unfixed, numthreads, reduction, storage, max_dense_bytes, min_work, min_work_cost and precision); otherwise it builds a new setup and keeps that. The structure is the number, types and sizes of the variables and, for each cost, its variables and its number of residuals; it is hashed at each call, which costs one pass over the variables and the costs. Values are not part of it: a call starts from the variables' values at the time of the call, and the costs' data are read when they are evaluated. The optimizer's workspace follows its own rule, that of OptimizationWorkspace.

ModelWorkspace() is empty and adapts to any call. The second form builds the setup and the optimizer's workspace for model, options and the keywords (the keywords of optimize!(model, options; ...) that decide the setup, with the same defaults); it is typed for them, so that a repeated call with the same arguments is type-stable and, after the first, allocates nothing. A call it cannot hold (another kind of unfixed, another formulation) empties it, with a one-time warning, and builds its setup every time. empty! empties a workspace, and isempty tells whether it holds a setup.

optimize(model, ...), which solves a copy of the model, never reuses the setup, since each copy is another Model.

Example

workspace = ModelWorkspace(model, options; unfixed = 2)
for t in 1:10
    # ... change the values of the variables or the costs' data ...
    optimize!(model, options; unfixed = 2, workspace)
end

For alternation, each of a set of variables optimized on its own:

NLLSModel.optimizesingles! — Function
optimizesingles!(model::Model, options, variables; precision=Float64, max_dense_bytes=268435456) -> OptimizationResult

Optimize each of variables on its own, the other variables fixed, and write each solution into model.variables: one step of an alternation, such as every landmark of a bundle adjustment with the cameras held. variables is a type (every variable that isa it) or a vector of variable indices. Defined when SecondOrderOptimization is loaded; options is an OptimizationOptions.

Each variable is solved on its own costs, as optimize!(sub, options; unfixed = i, numthreads = 1) solves it on a subproblem! sub that holds them, and in this order: by size, then by type (in the order in which the types first appear in variables), and otherwise in the order given. The order matters only when two of the variables share a cost: each is solved with those before it at their new values. The variables of one type and size share one linear system and one optimizer workspace, so after the first of them a variable costs no allocation; this is what makes it faster than that loop.

It returns the sum (+) of the variables' results: the costs, counts and times summed, the termination flags or-ed. With no variable to optimize, every number in the result is zero. It runs on one thread. precision and max_dense_bytes are as for optimvars; a variable's system is static or dense, never sparse or eliminated. An index out of range, or given twice, is an ArgumentError.

Example

optimizesingles!(model, OptimizationOptions(), SVector{3, Float64})   # every landmark, the cameras held
optimizesingles!(model, OptimizationOptions(), [1, 2, 3])             # the first three variables

NLLSModel.recommendoptimizer — Function
recommendoptimizer(model::Model; unfixed=nothing, numthreads=StaticInt(Threads.nthreads()), max_dense_bytes=268435456) -> OptimizationRecommendation

Recommends how to solve model, from its structure and its current values: a formulation (:hessian, the Hessian, or :jacobian, the residual and the Jacobian), the reduction and storage, a linear solver and an iterator, each chosen by a hand-written rule. Displaying the result explains each choice and prints the equivalent call to optimize!(model, options; ...); with SecondOrderOptimization loaded, optimize!(model, rec) runs it.

It builds the Hessian path as optimize!(model, options) does with reduction = storage = :auto, then builds, linearizes and factorizes its linear system once, at the model's current values, to measure the spread of the Hessian's diagonal (largest over smallest), a lower bound on the condition number of the Jacobi-scaled Hessian D^-½ H D^-½ (by 2 steps of inverse iteration), and the time of a cost evaluation, a linearization and an undamped solve. When every cost is an AbstractResidual and the Hessian is ill-conditioned (the estimate is at least 1.0e12) or could not be factorized undamped, it also tests the rank of the Jacobian J: it takes the weakest direction w of the scaled Hessian (from the undamped factorization, or else from the first of the scaled dampings H + λD, λ in (1.0e-14, 1.0e-12, 1.0e-10), that factorizes), refines it by 1 step of inverse iteration on JᵀJ, with products of J, and reads t = ‖J D^-½ w‖, with ‖w‖ = 1: the smallest of the readings before and after each step. The column-scaled J D^-½ has unit columns, so t is an upper bound on its smallest singular value. This evaluates the Jacobian once, through optimvars_nls without elimination; the first such call compiles the Jacobian evaluators. Then:

  • Formulation: :hessian when the Hessian is well conditioned, or when a cost is not a residual, except for the normal equations from the Jacobian, below. Otherwise the rank test decides: J is numerically rank-deficient when t is below 1.0e-12 (a gauge freedom, for example), which factorizing J would not help and damping handles, so :hessian; otherwise J has full numerical rank, and :jacobian, since forming JᵀJ squares its conditioning. Where the test cannot run, :hessian: the Hessian has a diagonal entry that is not positive, no damping tried factorizes it (it is indefinite, say), or optimvars_nls cannot build the model (an unfixed adaptive kernel, for example). The normal equations from the Jacobian: :jacobian with the normal equations formed from a dense Jacobian when every cost is a residual, the Hessian is well conditioned (no rank test), the Hessian path's system is dense (not static, sparse or eliminated), the dimension is above 12, and building the Hessian cost by cost is estimated to take at least 2.0 times the multiply-adds of one product JᵀJ: Σ n_c² (m_c + 2.5) over the costs (m_c residual rows, n_c unfixed dimensions; 2.5 stands for one load-add-store into the Hessian) against M N² / 2 for the M × N Jacobian; and the dense Jacobian fits max_dense_bytes and optimvars_nls builds it.
  • Reduction and storage: what :auto builds, on the formulation's path; for the normal equations from the Jacobian, reduction = :none and storage = :dense, which the product needs.
  • Linear solver: on the Hessian path, :cholesky for a static, dense or eliminated system and :ldl for a sparse one (what linsolver = :auto uses), but :ldl whenever a cost is not a residual, since the Hessian can then be indefinite; on the Jacobian path :qr, and :cholesky (of JᵀJ, formed from the Jacobian in one product) for the normal equations from the Jacobian.
  • Iterator: :dogleg when the undamped solve succeeded, the condition estimate is below 1.0e8, the diagonal's spread is below 1.0e6 and a solve takes at least as long as a linearization; otherwise :levenbergmarquardt_dtd when the spread is at least 1.0e6; otherwise :levenbergmarquardt.

Every threshold is a starting value, not yet measured against benchmarks (2.5 and 2.0 too). The model's variables are not changed. A model whose cost, gradient or Hessian is not finite at its current values is an ArgumentError.

The two work estimates count arithmetic only: not threads (the Hessian is filled cost by cost on Polyester's threads, the product JᵀJ by BLAS), and not a cost whose Jacobian block is mostly zeros. The iterator's test of a solve against a linearization still reads the Hessian path's times.

The rank test detects a null space of J; it is not an estimate of J's condition number. Its known limits: a null space together with a remainder whose smallest scaled singular value is below about 1e-7 reads as full rank, and goes to the Jacobian path; and a full-rank J with a condition number near 1e13 reads about 1e-8 when damping was needed, so it too goes to the Jacobian path.

The keywords are those of optimvars, with the same meanings and defaults; the recommendation keeps them, and optimize!(model, rec) uses them.

Example

rec = recommendoptimizer(model)   # displays the explanation and the call
result = optimize!(model, rec)    # with `using SecondOrderOptimization`

NLLSModel.computeresjac — Function
computeresjac(varflags, cost::AbstractResidual, vars...) -> (res, jac)

Computes the residual vector and Jacobian matrix for active variables indicated by bitmask varflags. Defaults to ForwardDiff automatic differentiation when not specialized.

Rules for user code, because residuals are evaluated on several threads at once:

  • Arrays returned from computeresjac (or computecostgradhess) must not be shared with other residuals. Returning arrays that the residual owns or that are local to the call is fine; a buffer reused by two residuals evaluated at the same time is not.
  • The code must itself be single-threaded (no BLAS on large matrices, no Threads.@threads). If it needs BLAS, call BLAS.set_num_threads(1) in the application.

The residual can be a Number, a Vector or any StaticVector (SVector, MVector, ...). The Jacobian can be an SMatrix, a Matrix (or any strided matrix of hardware floats) or, for a scalar residual, the adjoint of the gradient vector. The two need not both be static or both dynamic: a static residual with a Matrix Jacobian is fine, as is a Vector residual with an SMatrix. The kernels for products of the Jacobian are chosen by the types of the residual and Jacobian and by the type of nres (see nres).

Robust Cost Functions

NLLSModel.AbstractRobustifier — Type
AbstractRobustifier

Abstract base type for robust kernels ρ(s) of the squared residual norm s = ‖r‖². A residual's cost is 0.5·ρ(s). The convention is ρ(s) = −2 log p(r), with p a density over r; a fixed kernel may drop any constant term (NoRobust is ρ(s) = s). A kernel defines robustify, and may define robustifydcost (otherwise computed by automatic differentiation).

NLLSModel.AbstractAdaptiveRobustifier — Type
AbstractAdaptiveRobustifier <: AbstractRobustifier

Abstract base type for robust kernels with parameters that can be optimized: a variable of the model, the first variable of an AbstractAdaptiveResidual. An adaptive kernel returns ρ(s) = −2 log p(r) exactly, with every term that depends on its parameters or on the residual length d, which it carries (as static(d) in its constructor; addcost! checks it against nres). A density can exceed 1, so its cost can be negative. See ContaminatedGaussian and GaussianPlusUniform.

NLLSModel.ContaminatedGaussian — Type
ContaminatedGaussian(s1, s2, w, d::StaticInt)

Adaptive robust kernel for residuals of length d: a mixture of two zero-mean Gaussians of standard deviations s1 and s2, with weights w and 1 − w,

ρ(s) = −2 log(w N_d(s; s1) + (1 − w) N_d(s; s2)), where N_d(s; σ) = (2πσ²)^(−d/2) exp(−s/(2σ²)) and s = ‖r‖².

s1, s2 and w are the kernel's variables (optimized as log(1/s1), log(1/s2) and logit(w)); the arguments are promoted to one float type. The components are kept in the order given: the density is the same with (s1, w) and (s2, 1 − w) exchanged, so which is the narrow one is the caller's choice. Pass d as static(d): it must equal nres of the residuals that use the kernel, which addcost! checks. As ρ is −2 log p exactly, a cost can be negative.

Example

using Static
kernel = ContaminatedGaussian(1.0, 10.0, 0.8, static(1))
robustify(kernel, 0.5)
NLLSModel.GaussianPlusUniform — Type
GaussianPlusUniform(sigma, w, d::StaticInt; volume)

Adaptive robust kernel for residuals of length d: a Gaussian of standard deviation sigma and weight w, plus a uniform outlier density (1 - w) / A with A = volume,

ρ(s) = −2 log(w N_d(s; sigma) + (1 − w)/A), where N_d(s; σ) = (2πσ²)^(−d/2) exp(−s/(2σ²)) and s = ‖r‖².

sigma and w are the kernel's variables (optimized as log(1/sigma) and logit(w)). The outlier volume A is supplied, finite and positive, and never optimized; a residual can hand over its own with withlogvolume. The uniform term is not truncated to a region: the kernel sees only s. Pass d as static(d): it must equal nres of the residuals that use the kernel, which addcost! checks. As ρ is −2 log p exactly, a cost can be negative.

Example

using Static
kernel = GaussianPlusUniform(1.0, 0.9, static(2); volume = 100.0)
robustify(kernel, 0.5)
NLLSModel.withlogvolume — Function
withlogvolume(kernel::GaussianPlusUniform, logvolume) -> GaussianPlusUniform

The same kernel with the logarithm of its outlier volume replaced by logvolume (converted to the kernel's element type): a copy of the fields, of the same concrete type. A residual whose outliers have a volume of their own hands it over this way, from getvars (an adaptive kernel) or robustkernel (a fixed one).

Example

using Static
kernel = GaussianPlusUniform(1.0, 0.9, static(2); volume = 100.0)
withlogvolume(kernel, log(250.0)) == GaussianPlusUniform(1.0, 0.9, static(2); volume = 250.0) # true
NLLSModel.optimizerobustifier — Function
optimizerobustifier(kernel, s[, logvolume]; maxiters = 10, rtol = 1e-6, wprior = (1.0, 1.0)) -> kernel

Fit an adaptive kernel (ContaminatedGaussian or GaussianPlusUniform) to the squared residual norms s (sᵢ = ‖rᵢ‖²) by expectation-maximization, and return the fitted kernel, of the same type; kernel is the start. For a GaussianPlusUniform, logvolume (of the length of s) gives each residual's outlier log volume log Aᵢ; omitted, every residual uses the kernel's own, which the fitted kernel keeps.

  • maxiters: the most iterations.
  • rtol: stop when the kernel's parameters change by less than this, relatively.
  • wprior = (α, β): a Beta prior on the first component's weight w, as pseudo-counts; both finite and at least 1. (1, 1) is no prior.

It also stops when the responsibilities are all in one component or a scale would not be finite and positive (all the inlier residuals zero, say), returning the kernel it has; an empty s returns kernel. It allocates nothing.

Example

using Static
s = [0.1, 0.5, 2.0, 0.3, 80.0, 0.7, 1.2, 150.0]
kernel = optimizerobustifier(ContaminatedGaussian(0.5, 5.0, 0.5, static(1)), s)
NLLSModel.optimizerobustifier! — Function
optimizerobustifier!(model::Model, index; s = Float64[], logvolume = Float64[], maxiters = 10, rtol = 1e-6,
                     wprior = (1.0, 1.0)) -> cost

Fit the adaptive kernel model.variables[index] (a ContaminatedGaussian or a GaussianPlusUniform) to the residuals that use it, at the model's current variables, with optimizerobustifier; write it back, and return the model's new cost. The residuals are the AbstractAdaptiveResiduals whose first variable is index; for a GaussianPlusUniform each residual's outlier log volume is that of the kernel its getvars hands over (see withlogvolume). A residual holding a fixed kernel through robustkernel is not visited. With no residual using the kernel, it is unchanged.

s and logvolume are buffers, resized to the number of residuals: a caller who keeps them allocates nothing after the first call. The other keywords are those of optimizerobustifier.

To alternate between fitting the kernel and optimizing the other variables, fix the kernel and fit it in the optimizer's callback, with OptimizationOptions(callbackchangesstate = true): callback = (cost, x, data, iteratedata) -> (optimizerobustifier!(model, index; s, logvolume), 0).

NLPModels Integration

NLLSModel.NLPLSModel — Function
NLPLSModel(problem::Model; unfixed=nothing, numthreads=StaticInt(Threads.nthreads()), reduction=:auto, storage=:auto, min_work=4000, min_work_cost=120, precision=Float64, name="NLPLSModel")

Wraps a Model as an NLPModels.AbstractNLPModel for use with general nonlinear programming solvers such as JSOSolvers, Ipopt, and Optim.

Requires loading NLPModels:

using NLLSModel, NLPModels
nlp = NLPLSModel(problem)

Arguments

  • problem::Model: The nonlinear least-squares problem to wrap.

Every unfixed variable must update by plain addition and pack into a flat Float64 vector (as for flat_optimvars_nls), since the solver steps by adding to the flat vector of the variables' values; otherwise it throws an ArgumentError, before anything is evaluated.

It works on the full system: reduction = :auto means :none, and :eliminate is an ArgumentError. name is the name given to the model's metadata (default "NLPLSModel").

Features

  • Automatically selects dense or block-sparse Hessian representations based on problem structure.
  • Implements obj, grad!, objgrad!, hess_structure!, hess_coord!, and hprod!.
  • Caches cost, gradient, and Gauss-Newton Hessian evaluations across queries at the same point.
  • Transfers solution vectors back to problem.variables via syncvars!.

Keywords

The same for optimvars, optimvars_nls, flat_optimvars_nls, optimize!(model, options), NLPLSModel and NLLSNLSModel.

  • unfixed = nothing: which variables to optimize: a variable index, a variable type, a Boolean mask or a list of indices. nothing optimizes all of them; the others are left untouched.
  • numthreads = StaticInt(Threads.nthreads()): the most threads an evaluation uses (StaticInt or Integer).
  • reduction = :auto: whether eliminable variables are eliminated (the Schur complement). :auto eliminates when the model has iseliminable variables and the structure fits, and otherwise does not; :eliminate eliminates or throws an ArgumentError; :none never eliminates. The rule is the same on the Jacobian path (the residual and Jacobian, where the eliminated variables are eliminated by QR), which also needs every eliminated variable to be in a cost. The wrappers that hand a plain Jacobian to external solvers (flat_optimvars_nls, NLLSNLSModel) never eliminate: there :auto does not eliminate and :eliminate is an ArgumentError. A single unfixed variable is never eliminated under :auto, and :eliminate is an ArgumentError there.
  • storage = :auto: storage of the matrix the solver receives: the Hessian, the reduced system under elimination (on either path), or the Jacobian. :auto chooses from the structure (the sparsity of the Hessian, the predicted fill of the reduced system's Cholesky factor, or the fill of the Jacobian); :dense and :sparse force the choice. On the Jacobian path the Jacobian is a Matrix{Float64} or a SparseMatrixCSC{Float64, Int}, and optimize!(...; formulation = :jacobian) hands either to the optimizer. On the Hessian path a single unfixed variable's Hessian is always dense, so :sparse is an ArgumentError there.
  • max_dense_bytes = 268435456 (256 MiB): under storage = :auto a dense matrix larger than this is not chosen (it is stored sparse instead); under :dense a larger one is an ArgumentError saying how large it would be, raised before it is allocated. A single variable's Hessian has no sparse alternative, so above the cap it is an ArgumentError either way.
  • min_work: per-thread floor of the fill, in the work estimate of the formulation: on the Hessian path (the Hessian fill, forming JᵀJ and Jᵀr; default 4000) one number written, per cost m * n * (n + 1); on the Jacobian path (the Jacobian fill, writing r and J; default 280) one entry of r or J written, per cost m * (n + 1).
  • min_work_cost = 120: per-thread floor of a cost evaluation, one residual entry, per cost m.
  • precision = Float64: the element type of the linear system, Float64 or Float32 (anything else is an ArgumentError). With Float32 the Hessian (on the Jacobian path the Jacobian), its reduction and its factorization are single precision; the variables, the residuals, the cost, the gradient and the step stay Float64, each cost's derivatives are computed in Float64 and narrowed as they are added into the system. The byte counts of max_dense_bytes and of the dense-or-sparse decisions are of the system in this precision. Which solvers offer Float32 is DampedLinearSolve's table (its "Precision"); one that does not is an ArgumentError when the system is built. The wrappers that hand a plain system to external solvers (flat_optimvars_nls, NLPLSModel, NLLSNLSModel, nls_callbacks) take Float64 only.

Each kind of work is split over clamp(work ÷ floor, 1, numthreads) threads: one thread when its estimate is below twice the floor, and every thread at a floor of 0. The costs of each type are split into one chunk per thread, so the count is also never more than the largest number of costs of one type: a thread beyond that would have nothing to do. The Hessian fill uses at most 4 threads: each thread fills its own copy of the linear system, which costs work in proportion to the size of the system, so on large systems more threads were measured to be slower (the number of copies is also capped by memory). The defaults were measured on cheap residuals, on one machine; a costly residual could thread earlier than they let it.

Here m is a cost's residual length (1 for a general AbstractCost) and n the total dimension of its unfixed variables; each estimate is summed over all costs and computed once, at setup. The work of the residual functions themselves is not estimated.
