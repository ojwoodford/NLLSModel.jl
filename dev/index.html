NLLSModel.jl

Nonlinear Least Squares & Factor Graph Modeling in Julia

NLLSModel.jl is a high-performance framework for formulating nonlinear least squares and general factor-graph optimization problems:

\[\min_{\mathbf{x}} \sum_{i} \frac{1}{2} \rho_i \left( \| r_i(\mathbf{x}_{S_i}) \|^2 \right) + \sum_{j} c_j(\mathbf{x}_{S_j})\]

where:

  • \[\mathbf{x} = \{ \mathbf{x}_1, \dots, \mathbf{x}_N \}\]

    are variable blocks (scalars, static vectors, dynamic vectors, or custom manifolds).

  • \[r_i\]

    is the $i$-th residual function depending on a subset of variables $\mathbf{x}_{S_i}$.

  • \[\rho_i\]

    is an optional robust loss kernel (HuberKernel, Huber2oKernel, GemanMcclureKernel, GemanMcclure2oKernel, ContaminatedGaussian, GaussianPlusUniform, Scaled).

  • \[c_j\]

    is an optional general scalar cost block (AbstractCost).

Features

  • Heterogeneous Variable & Cost Blocks: Store variable blocks and cost types with zero type-instability.
  • Fast Block Linear Systems: Custom DenseBlockLinearSystem and SparseBlockLinearSystem (from BlockLinearSystems.jl) tailored for sparse $LDL^T$, Cholesky, and QR factorizations.
  • Automatic Differentiation: Evaluates residual Jacobians and cost gradients/Hessians automatically via ForwardDiff.jl, or uses user-supplied analytic derivatives via computeresjac.
  • Robust M-Estimators: First- and second-order robust kernels plus adaptive robustifiers (ContaminatedGaussian, GaussianPlusUniform).
  • Single Precision: precision = Float32 holds the linear system (Hessian or Jacobian, its reduction and factorization) in single precision and everything else in double; see Linear Solvers & Sparsity.
  • One-Call Solving: optimize!(model, options) (with using SecondOrderOptimization) solves the model and writes the solution back.
  • Solver-Agnostic Extraction: For advanced use, optimvars returns (f, fdf!, x0, H) for custom outer loops or other optimizers.
  • Multi-threaded Evaluation: Automatic thread-parallel residual and Hessian evaluation via Polyester.jl.

Quick Start

using NLLSModel, SecondOrderOptimization
using Static, StaticArrays

# 1. Define a custom residual struct
struct PointDistanceResidual <: AbstractResidual
    target::SVector{2, Float64}
    varind::Int
end

NLLSModel.ndeps(::PointDistanceResidual) = static(1)
NLLSModel.nres(::PointDistanceResidual) = static(2)
NLLSModel.varindices(res::PointDistanceResidual) = SVector(res.varind)
NLLSModel.getvars(res::PointDistanceResidual, vars::Vector) = (vars[res.varind]::SVector{2, Float64},)
NLLSModel.computeresidual(res::PointDistanceResidual, x) = x - res.target
Base.eltype(::PointDistanceResidual) = Float64

# 2. Build the model
problem = Model(SVector{2, Float64}, PointDistanceResidual)
idx = addvariable!(problem, SVector(0.0, 0.0))
addcost!(problem, PointDistanceResidual(SVector(3.0, 4.0), idx))

# 3. Solve. The solution is written back into the model
result = optimize!(problem, OptimizationOptions(iterator = :levenbergmarquardt))
println("Estimated variable: ", problem.variables[idx])
println("Final cost: ", result.bestcost)

optimize!(model, options) is defined by a package extension: it needs using SecondOrderOptimization (NLLSModel already depends on BlockLinearSystems). optimize(model, options) returns (model_copy, result) and leaves model unchanged. The keywords reduction and storage choose the linear-system layout; see Linear Solvers & Sparsity. Every way of building or optimizing a model takes the same keywords (see optimvars).

Jacobian formulation

optimize!(model, options; formulation = :jacobian) solves the same model from the residual vector and the Jacobian instead of the normal equations. Each step is a QR factorization of the Jacobian (dense, or SuiteSparse's sparse QR), or with elimination a QR of each eliminated variable's rows and a solve of the reduced problem, so JᵀJ is not formed (only the reduced system's normal equations, when linsolver asks for them) and the conditioning is that of J, not its square. Without elimination and with a dense Jacobian, linsolver = :cholesky or :ldl instead forms the normal equations from J once per linearization: cheaper than QR when there are many more residuals than variables, but with the squared conditioning. Use it when the model is ill conditioned (the normal equations stall above the minimum).

result = optimize!(problem, OptimizationOptions(iterator = :levenbergmarquardt); formulation = :jacobian)

What it supports, by the reduction and storage it ends up with and the linsolver given in OptimizationOptions:

reductionstorageJacobian prototypelinsolver
no eliminationdenseMatrix{Float64}:auto, :qr; :cholesky, :ldl (the normal equations, formed from J); :lsmr (with Krylov.jl)
no eliminationsparseSparseMatrixCSC{Float64, Int}:auto, :qr; :lsmr (with Krylov.jl)
eliminationdenseSchurBlockJacobian{Float64, Matrix{Float64}}:auto, :qr, :cholesky, :ldl; :lsmr (with Krylov.jl)
eliminationsparseSchurBlockJacobian{Float64, SparseMatrixCSC{Float64, Int}}:auto, :qr, :cholesky, :ldl; :lsmr (with Krylov.jl)

reduction and storage are as for the Hessian path, :auto included: elimination when the model has eliminable variables and the structure fits (on the Jacobian path also: each eliminated variable is in a cost), the reduced system stored by the Hessian path's rule, and without elimination the Jacobian's storage from its fill, never dense above max_dense_bytes. The linsolver values are those SecondOrderOptimization accepts for each prototype: its rules, the linear system of each row and the iterators it takes are in the "Supported combinations" table of its JacobianObjective docstring. Any other combination is an ArgumentError before anything is evaluated.

Also:

  • every cost must be a non-adaptive AbstractResidual, and no adaptive kernel variable may be unfixed. Otherwise the error from optimvars_nls is rethrown with the prefix formulation = :jacobian:, as is a dense Jacobian forced above max_dense_bytes (default 256 MB), raised before it is allocated;
  • min_work is the floor of the residual and Jacobian fill (the tables, with elimination), in its own work estimate, with its own default;
  • there is no robust-mode keyword: each cost's kernel decides how its rows enter (see the robust-kernel tutorial), so choosing HuberKernel or Huber2oKernel chooses first- or second-order treatment.

formulation is a keyword of optimize! and optimize only. It is not an OptimizationOptions field and is not inferred from linsolver; a caller of optimvars or optimvars_nls chooses by which one they call.

Repeated solves

A model solved many times (in a loop that changes its data, or in alternation) can keep what each solve builds in a ModelWorkspace: the model's setup (the linear system's layout, its storage and the functors) and the optimizer's state. Built for a model, options and keywords, it makes a repeated call with the same arguments allocation-free after the first; a change to the model's structure or to the keywords builds a new setup.

workspace = ModelWorkspace(problem, options; unfixed = 2)
for t in 1:10
    # ... change the values of the variables or the costs' data ...
    optimize!(problem, options; unfixed = 2, workspace)
end

Advanced Use: optimvars

Use optimvars when you need the pieces yourself: a custom outer loop, a reused OptimizationWorkspace, the NLPModels wrapper, or another optimizer.

f, fdf!, x0, H = optimvars(problem)
result = optimize!(x0, HessianObjective(f, fdf!; H), OptimizationOptions(iterator = :levenbergmarquardt))
syncvars!(problem, fdf!, x0)

A single variable of static size is immutable: call x, result = optimize(x0, HessianObjective(f, fdf!; H), options) and syncvars!(problem, fdf!, x).
